thinking-orbs · Lynx port

The same orb, drawn two ways, one on top of the other.

Lynx has no canvas. The port draws every dot as its own <view>, moved and re-tinted each frame by one main-thread style write. Everything on this page is the real ReactLynx component running in Lynx for Web — the same parity.web.bundle the CI harness screenshots — next to the web library's own canvas painter. Nothing here is a recording.

1 · Parity, live

Both sides get the same frozen engine instant. The third tile stacks them with mix-blend-mode: difference, so identical pixels come out black — then multiplies what is left by the amplifier, because at 1× you would see nothing.

Measured headlessly over all 72 combinations (9 states × 2 sizes × 2 themes × 2 instants): worst mean 0.072/255, worst p99 1.0, total ink 0.995–1.001× of the web. Both sides share a rasteriser here — that is the point. It leaves the port's own draw sequence as the only variable.

2 · Moving, in a real Lynx runtime

The example app, unmodified: nine states at both tuned sizes, its own theme toggle, animating on the main thread. Tap the pill inside the card to flip the theme.

3 · What it costs

One element write per dot per frame is the whole cost model, so it scales with dot count. The meter is this page's own frame cadence, measured live while the orbs animate — drop it to shaping (24 dots) or push it to composing (566) and watch the number move.

Desktop-browser numbers through the DOM. Native Lynx writes go to the engine instead, and nothing here has run on a device yet — this is a ceiling check on the approach.

4 · Reproduce it

git clone https://github.com/Huxpro/libraries
cd libraries/packages/thinking-orbs/ports/lynx/example  && npm i && npx rspeedy build
cd ../thinking-orbs-lynx && npm i
npm run verify:golden   # engine vs spec/orbs-golden.json — 70,115 values
npm run parity          # this page's diff, headless, with numbers
npm run live-check      # motion, pause, reduced motion, theme, cadence
